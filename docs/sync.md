# Синхронизация

Протокол обмена данными между устройством пользователя и сервером.
Реализация — задача T11 (`crates/core/src/sync`) и этап M8.

## 1. Принципы

1. **Устройство — источник истины для своих данных.** Сервер хранит копию,
   но не диктует, что «правильно».
2. **Сервер — арбитр и хаб.** Он присваивает порядковые номера изменениям и
   раздаёт их остальным устройствам.
3. **Единица синхронизации — запись**, а не вся коллекция. Записи независимы,
   поэтому конфликты редки и локальны.
4. **Удаление — это надгробие** (`deleted_at`), а не физическое удаление.
   Иначе удалённая на одном устройстве запись «воскреснет» с другого.
5. **Молчаливой потери данных нет.** Проигравшая версия сохраняется как
   конфликтная копия и показывается пользователю.

## 2. Поля, общие для синхронизируемых записей

| Поле | Кто заполняет | Смысл |
|---|---|---|
| `id` | клиент (UUID v4) | идентификатор, одинаковый на всех устройствах |
| `revision` | клиент | номер правки записи, только растёт |
| `sync_seq` | сервер | порядковый номер изменения у пользователя |
| `updated_at` | клиент и сервер | время последней правки |
| `device_id` | клиент | кто сделал последнюю правку |
| `deleted_at` | клиент | надгробие; `NULL` — запись жива |

Сервер хранит `sync_seq` прямо в строке таблицы. Индекс
`(user_id, sync_seq)` делает выборку «что нового» дешёвой.

### 2.1 Типы в коде

Всё это живёт в `crates/core/src/sync/mod.rs` и используется и сервером,
и десктопом:

| Тип | Что внутри | Зачем отдельный тип |
|---|---|---|
| `Revision(u64)` | счётчик правок | нельзя случайно передать номер изменения вместо ревизии |
| `SyncSeq(u64)` | позиция в серверной последовательности | отличается по смыслу от `Revision` |
| `DeviceId(Uuid)` | идентификатор установки | нужен для тайбрейка и разбора конфликтов |
| `Timestamp(i64)` | миллисекунды UTC от эпохи | одинаково хранится в Postgres и SQLite, нет зон |

`Timestamp` намеренно хранится числом, а не строкой: сравнение — это
сравнение целых, без разбора RFC 3339 и без сюрпризов с часовыми поясами.
В JSON для API он превращается в RFC 3339 на границе.

## 3. Состояние клиента

```text
sync_state:  last_sync_seq        -- до какого номера клиент в курсе
outbox:      локальные изменения, ожидающие отправки
conflicts:   проигравшие версии, ожидающие решения пользователя
```

`outbox` нужен, чтобы переживать обрыв связи: изменения не теряются, пока
сервер не подтвердил приём.

## 4. Потоки

### POST /sync/push

Клиент отправляет пачку локальных изменений:

```json
{
  "batch_id": "b7f1…",
  "device_id": "d3a2…",
  "changes": [
    {
      "entity": "item",
      "id": "8a1f…",
      "revision": 4,
      "updated_at": "2026-11-02T12:00:00Z",
      "deleted_at": null,
      "payload": { "title": "Interstellar", "rating": 9 }
    }
  ]
}
```

Сервер для каждого изменения:

1. Проверяет, что запись принадлежит пользователю.
2. Если `revision` совпадает с уже применённой — пропускает (идемпотентность).
3. Если `revision` больше серверной — применяет, присваивает новый `sync_seq`.
4. Если `revision` меньше — сравнивает `updated_at`; победитель остаётся,
   проигравший уходит в конфликтные копии.

Ответ:

```json
{
  "applied": ["8a1f…"],
  "conflicts": [{ "id": "9b2c…", "reason": "stale_revision" }],
  "last_seq": 1042
}
```

### GET /sync/pull?since=N&limit=500

Отдаёт все записи пользователя с `sync_seq > N`, включая надгробия, в порядке
возрастания `sync_seq`.

```json
{
  "changes": [ { "entity": "item", "id": "…", "revision": 5, "sync_seq": 1043,
                 "deleted_at": null, "payload": { … } } ],
  "next_since": 1043,
  "has_more": false
}
```

### GET /sync/status?since=N

Дешёвая проверка «есть ли что-то новое». Не читает сами записи.

```json
{ "last_seq": 1045, "changes_after": 3 }
```

Десктоп опрашивает этот эндпоинт раз в 30 секунд и при возврате фокуса в окно;
если `changes_after > 0` — показывает баннер «Есть изменения в вебе».

## 5. Разрешение конфликтов

Правило одно и реализовано чистой функцией в
`crates/core/src/sync/merge.rs`; им пользуются и сервер, и клиент, поэтому
вердикт всегда совпадает.

| Ситуация | Правило |
|---|---|
| Состояния полностью совпадают | `Duplicate` — ничего не делаем (повторная отправка) |
| `updated_at` у входящего больше | `TakeIncoming` — входящая версия побеждает |
| `updated_at` у входящего меньше | `KeepStored` — побеждает сохранённая, входящая идёт в конфликтные копии |
| `updated_at` равны | побеждает больший `device_id` (детерминированно на обеих сторонах) |
| Удаление против правки | удаление не особенное: побеждает более поздняя операция |
| Удаление победило, но была правка | запись остаётся удалённой, текст правки — в конфликтной копии |
| Повторная отправка той же пачки | `batch_id` уже применён → no-op |

`Revision` не участвует в выборе победителя: она нужна, чтобы отличить
повторную отправку от настоящей правки и пометить конфликт. Порядок
определяет время, а при равном времени — `device_id`.

Конфликтная копия — отдельная запись со своим `id`, которая видна в разделе
«Расхождения» и позволяет выбрать версию вручную.

## 6. Инварианты

1. `sync_seq` строго возрастает и уникален в пределах пользователя.
2. У каждой записи ровно один `sync_seq`.
3. `revision` на клиенте никогда не уменьшается.
4. `push` с уже применённым `batch_id` не меняет данные.
5. После успешного `push` + `pull` состояние клиента и сервера совпадает.

## 7. Сценарии, которые обязаны работать

| № | Сценарий | Ожидание |
|---|---|---|
| 1 | Новое устройство | `pull(since=0)` отдаёт всё, включая надгробия |
| 2 | Два устройства правили офлайн | конфликт, обе версии сохранены |
| 3 | Удаление против правки | запись не воскресает, текст правки доступен |
| 4 | Обрыв посреди `push` | после повтора данные не дублируются |
| 5 | Повторная отправка пачки | no-op, `sync_seq` не растёт |
| 6 | Правка в вебе при открытом десктопе | десктоп показывает баннер в течение 30 с |
| 7 | Третье устройство догоняет | получает все изменения в правильном порядке |

## 8. Что не синхронизируется

- сессии и токены — принадлежат конкретному устройству;
- настройки интерфейса (тема, фильтры) — локальные;
- медиафайлы — отдельный механизм, появится после 0.2.0.

## 9. Тесты правила слияния

`crates/core/src/sync/merge.rs` покрывает таблицу из раздела 5:

- идентичные состояния → `Duplicate`;
- более поздняя правка побеждает, более ранняя проигрывает;
- равное время → выигрывает больший `device_id` (в обе стороны симметрично);
- два устройства правили офлайн от одной ревизии → конфликт разрешается
  одинаково независимо от порядка прихода;
- удаление позже правки → удаление побеждает; правка позже удаления → правка
  побеждает;
- большая `Revision` при старом времени не побеждает.

## 10. Открытые вопросы
