# Синхронизация — контракт v1

**Статус:** заморожен 6 ноября 2026.  
**Версия протокола:** `1` (`X-Sync-Version: 1`).  
**Реализация:** T96 (`POST /devices`), T97 (`sync_seq`), T98
(`POST /sync/push`), T99 (`GET /sync/pull`), T100 (`GET /sync/status`) и
T101 (conflicts) готовы.  
**Не входит в v1:** коллекции, медиа, настройки, сессии, комментарии.

Любое изменение полей, кодов ошибок или правил конфликтов требует
`X-Sync-Version: 2`. Добавление новых необязательных полей в ответ
совместимо с v1; клиент обязан их игнорировать.

## 1. Решения

1. **Содержимое принадлежит клиенту.** Клиент формирует `payload`,
   `revision` и `updated_at`.
2. **Порядок принадлежит серверу.** Сервер присваивает `sync_seq`.
3. **Сервер — арбитр конфликтов.** Вердикт определяется детерминированно,
   одинаково на сервере и клиенте.
4. **Удаление — надгробие.** Физического удаления синхронизированных записей
   в v1 нет.
5. **Потери данных нет.** Проигравшая версия сохраняется как конфликтная
   копия.
6. **Одна запись — одна единица синхронизации.** Пачка — только транспорт.

## 2. Заголовки и версия

| Заголовок | Обязателен | Значение |
|---|---|---|
| `Cookie: jey_session` | да | сессия пользователя |
| `X-Device-Id` | да, кроме `POST /devices` | UUID установки |
| `X-Sync-Version` | да для `/sync/*` | `1` |
| `Origin` | да для POST/PATCH/DELETE | разрешённый origin |
| `X-Request-Id` | нет | сквозной id для логов |

Неизвестная версия → `400 unsupported_sync_version`.  
Незарегистрированный `X-Device-Id` → `400 unknown_device`.

## 3. Сущности v1

### 3.1 `item`

Синхронизируются только записи владельца. Публичность, комментарии, теги
как отдельные сущности и коллекции в v1 не синхронизируются.

Поля конверта:

| Поле | Тип | Кто задаёт | Смысл |
|---|---|---|---|
| `entity` | `"item"` | клиент | тип сущности |
| `id` | UUID v4 | клиент | одинаковый на всех устройствах |
| `revision` | integer ≥ 1 | клиент | монотонный номер правки |
| `sync_seq` | integer ≥ 0 | сервер | позиция изменения у пользователя |
| `updated_at` | RFC 3339 UTC | клиент | время правки |
| `deleted_at` | RFC 3339 UTC или `null` | клиент | надгробие |
| `payload` | object или `null` | клиент | содержимое; `null` у надгробия |

`payload`:

```json
{
  "kind": "movie",
  "title": "Interstellar",
  "subtitle": "Christopher Nolan",
  "year": 2014,
  "status": "done",
  "rating": 9,
  "review": "Публичная рецензия",
  "body": "Личная заметка",
  "source_url": null,
  "cover_key": null,
  "details": {},
  "tags": ["sci-fi", "nolan"]
}
```

Правила:

- `kind`: `movie`, `tv`, `anime`, `book`, `game`. Устаревшие `image` и `other`
  могут читаться, но новые клиенты их не создают.
- `status`: `planned`, `in_progress`, `done`, `dropped`.
- `body` — приватная заметка, никогда не попадает в публичный API.
- `details` — JSON-объект, версия v1 его не интерпретирует.
- `cover_key` — ключ медиа; сам файл в v1 не синхронизируется.
- `payload` не меняется при `deleted_at != null`;
- tombstone для записи, которую сервер ещё не видел (локальный create+delete
  до первого push), — no-op, а не ошибка всей пачки.
- `updated_at` не может быть больше серверного времени более чем на 5 минут;
  сервер нормализует такое значение до `now`. Клиенты обязаны использовать UTC.

### 3.2 `device`

```json
{
  "device_id": "d3a2c6a4-7c2f-4f1a-a3e8-2d6a8f0c1b77",
  "name": "Jey laptop",
  "platform": "linux"
}
```

`device_id` генерирует клиент при установке и хранит локально. Сервер
уникален по `(user_id, device_id)`. Повторная регистрация идемпотентна.

## 4. Эндпоинты

### 4.1 `POST /api/v1/devices`

Регистрирует установку. Требует сессию.

```json
{ "device_id": "…", "name": "Jey laptop", "platform": "linux" }
```

`201` или `200`:

```json
{ "device": { "device_id": "…", "name": "Jey laptop", "platform": "linux", "created_at": "2026-11-06T12:00:00Z" } }
```

Ошибки: `400 validation_error`, `400 unknown_device` не используется здесь,
`401 unauthorized`.

### 4.2 `POST /api/v1/sync/push`

Тело:

```json
{
  "batch_id": "b7f1c2d3-4e5f-4a6b-8c9d-0e1f2a3b4c5d",
  "changes": [
    {
      "entity": "item",
      "id": "8a1f0c62-3b9d-4a44-8f80-1c2f5d9b7a10",
      "revision": 4,
      "updated_at": "2026-11-06T12:00:00Z",
      "deleted_at": null,
      "payload": { "kind": "movie", "title": "Interstellar" }
    }
  ]
}
```

Ограничения:

- до **500** изменений в пачке;
- до **1 MiB** тела;
- `batch_id` — UUID, уникален для устройства;
- повторная пачка с тем же `(device_id, batch_id)` в течение **30 дней** —
  no-op, данные не меняются.

Ответ `200`:

```json
{
  "protocol_version": 1,
  "applied": [
    { "entity": "item", "id": "8a1f…", "revision": 4, "sync_seq": 1042 }
  ],
  "conflicts": [
    { "entity": "item", "id": "9b2c…", "reason": "stale_revision", "conflict_id": "c0d1…" }
  ],
  "last_seq": 1042
}
```

Коды:

- `400 validation_error` — неверные поля, лимит, неизвестная сущность;
- `400 unsupported_sync_version`;
- `400 unknown_device` — устройство не зарегистрировано;
- `401 unauthorized`;
- `403 forbidden` — чужая запись;
- `413 payload_too_large` — больше 1 MiB;
- `429 rate_limited` — слишком много пачек.

`conflicts` — не ошибка всей пачки. Принятые изменения применяются, а
конфликтующие возвращаются отдельно.

### 4.3 `GET /api/v1/sync/pull?since=N&limit=200`

Заголовки: `X-Device-Id`, `X-Sync-Version`.

- `since` — последний известный `sync_seq`, по умолчанию `0`;
- `limit` — 1..500, по умолчанию `200`;
- изменения строго по возрастанию `sync_seq`;
- надгробия включаются;
- `next_since` равен максимальному отданному `sync_seq` или `since`, если
  изменений нет.

Ответ `200`:

```json
{
  "protocol_version": 1,
  "changes": [
    {
      "entity": "item",
      "id": "8a1f…",
      "revision": 5,
      "sync_seq": 1043,
      "updated_at": "2026-11-06T12:01:00Z",
      "deleted_at": null,
      "payload": { "kind": "movie", "title": "Interstellar" }
    }
  ],
  "next_since": 1043,
  "has_more": false
}
```

### 4.4 `GET /api/v1/sync/status?since=N`

Дешёвая проверка. Не читает записи.

```json
{
  "protocol_version": 1,
  "last_seq": 1045,
  "changes_after": 3,
  "server_time": "2026-11-06T12:02:00Z"
}
```

`changes_after` — количество реальных записей с `sync_seq > since`, а не
арифметическая разница: после жёсткой очистки в последовательности есть
пропуски, и статус обязан совпадать с ближайшим `pull`.

### 4.5 Конфликты

`GET /api/v1/sync/conflicts` — неразрешённые конфликты:

```json
{
  "conflicts": [
    {
      "conflict_id": "c0d1…",
      "item_id": "8a1f…",
      "incoming": { "revision": 6, "updated_at": "…", "payload": {} },
      "stored": { "revision": 5, "updated_at": "…", "payload": {} },
      "created_at": "2026-11-06T12:00:00Z"
    }
  ]
}
```

`POST /api/v1/sync/conflicts/{conflict_id}/resolve`

```json
{ "keep": "incoming" }
```

или

```json
{ "keep": "stored" }
```

Решение удаляет конфликтную копию, применяет выбранную версию, увеличивает
`revision`, присваивает новый `sync_seq` и возвращает обновлённую запись.

## 5. Конфликты и слияние

Вердикт считается по `updated_at`, затем по `device_id`:

| Ситуация | Результат |
|---|---|
| Состояния совпадают | `Duplicate`, ничего не меняем |
| `updated_at` входящего больше | `TakeIncoming` |
| `updated_at` входящего меньше | `KeepStored`, входящая версия → конфликт |
| `updated_at` равны | побеждает больший `device_id` |
| Удаление позже правки | запись удалена, текст правки → конфликт |
| Правка позже удаления | запись восстановлена |
| Повтор `(device_id, batch_id)` | no-op |

`revision` не выбирает победителя. Она отличает повторную отправку от
настоящей правки и маркирует конфликт.

Правило живёт в `crates/core/src/sync/merge.rs`; сервер и клиент обязаны
использовать одну реализацию, а не дублировать условие.

## 6. Инварианты и хранение

1. `sync_seq` строго возрастает и уникален в пределах пользователя.
2. Каждая запись имеет ровно один текущий `sync_seq`.
3. `revision` на клиенте не уменьшается.
4. `push` с уже применённым `(device_id,batch_id)` не меняет данные.
5. После успешного `push` + `pull` состояние клиента и сервера совпадает.
6. Надгробия хранятся **бессрочно** в v1: объём мал, потеря удаления опаснее.
7. `batch_id` хранится **30 дней**.
8. `sync_seq` не переиспользуется даже после очистки старых данных.

## 7. Обязательные сценарии

| № | Сценарий | Ожидание |
|---|---|---|
| 1 | Новое устройство | `pull(since=0)` отдаёт всё, включая надгробия |
| 2 | Два устройства правили офлайн | конфликт, обе версии сохранены |
| 3 | Удаление против правки | запись не воскресает, текст правки доступен |
| 4 | Обрыв посреди `push` | повтор не дублирует данные |
| 5 | Повторная пачка | no-op, `sync_seq` не растёт |
| 6 | Правка в вебе при открытом десктопе | десктоп видит изменение в течение 30 с |
| 7 | Третье устройство догоняет | получает изменения в правильном порядке |
| 8 | Неверная версия протокола | `400 unsupported_sync_version` |
| 9 | Чужой `device_id` | `403 forbidden` |

## 8. Что не входит в v1

- коллекции и membership;
- медиа и обложки;
- комментарии, реакции, подписки;
- настройки интерфейса, тема, фильтры;
- сессии и токены;
- серверные публичные страницы как отдельные сущности.

Коллекции и медиа добавляются отдельными версиями протокола или
дополнительными эндпоинтами; они не должны менять смысл полей v1.

## 9. Изменение контракта

1. Новое необязательное поле ответа — совместимо.
2. Новый эндпоинт — совместим, если не меняет существующие.
3. Новый обязательный заголовок или изменение смысла поля — только
   `X-Sync-Version: 2`.
4. Любое изменение фиксируется здесь, в `docs/protocol.md` и
   `docs/openapi.yaml` одним коммитом.
