# Производительность запросов

Замеры: **2 ноября 2026**.
Окружение: Fedora 44, PostgreSQL 18.6, локальная машина, `target/debug`
(не release — для относительного сравнения это не важно, для абсолютных цифр
release будет быстрее).

## Данные

| Сущность | Объём |
|---|---|
| Пользователей | 1 (все записи принадлежат ему) |
| Записей | 10 000 |
| Тегов | 20 |
| Связей запись–тег | ~3 000 |
| `created_at` / `updated_at` | случайные за последний год / месяц |

Такой набор специально однобокий: все записи у одного пользователя, поэтому
фильтр `user_id` сам по себе не помогает — проверяются именно индексы под
сортировки и фильтры.

## Что было

Эндпоинты измерялись через `curl` (среднее из 5 запросов).

| Запрос | Было |
|---|---|
| `GET /items?limit=20` | **74 мс** |
| `GET /items?kind=movie` | 24 мс |
| `GET /items?tag=tag-5` | 28 мс |
| `GET /items?rating_min=9` | 19 мс |
| `GET /items?q=Title 5000` | 2,6 мс |
| `GET /stats` | 7,6 мс |

## Причина

Список собирался **одним запросом**: соединение с `item_tags` и `tags`,
`array_agg` по тегам, затем сортировка и `LIMIT 20`. PostgreSQL не может
применить `LIMIT` раньше агрегации: чтобы посчитать теги, ему нужны все 10 000
строк пользователя. Индекс по `(user_id, created_at)` в такой план не попадает.

## Что сделано

1. **Запрос разделён на две фазы** (см. `list_page` в `crates/api/src/items/repo.rs`):

   ```sql
   with page as (
       select i.id from items i
       where ...фильтры...
       order by ... limit $6
   )
   select ..., array_agg(t.name) ...
   from items i
   join page p on p.id = i.id
   left join item_tags ...
   ```

   Внутренняя часть использует индексы и останавливается на `limit` строках,
   внешняя агрегирует теги только для них.

2. **Добавлены частичные индексы** по живым записям
   (`migrations/0009_indexes.sql`):

   ```sql
   create index items_user_live_created_idx on items (user_id, created_at desc)
       where deleted_at is null;
   create index items_user_live_updated_idx on items (user_id, updated_at desc)
       where deleted_at is null;
   ```

   В модели local-first удалённые записи остаются надгробиями навсегда, поэтому
   индексы только по живым строкам со временем становятся заметно компактнее
   общих.

## Что стало

| Запрос | Было | Стало |
|---|---|---|
| `GET /items?limit=20` (created_desc) | 74 мс | **4,0 мс** |
| `GET /items?sort=updated_desc` | — | 5,0 мс |
| `GET /items?kind=movie` | 24 мс | 3,5 мс |
| `GET /items?tag=tag-5` | 28 мс | 4,5 мс |
| `GET /items?rating_min=9` | 19 мс | 3,3 мс |
| `GET /items?q=Title 5000` | 2,6 мс | 3,6 мс |
| `GET /stats` | 7,6 мс | 8,1 мс |

Поиск и статистика не менялись — они и так укладывались в бюджет: поиск
использует триграммные индексы, статистика — один проход по CTE.

## Планы

Список по дате после правки:

```
Limit
  ->  Index Scan using items_user_created_idx on items i
        (actual rows=22 loops=1)
Execution Time: 1,2 мс
```

Внутренняя часть выбирает 21 запись (лимит + 1 для проверки «есть ли ещё»)
и останавливается — остальные строки не читаются.

## Выводы

- Основной выигрыш дал **не индекс, а форма запроса**: агрегация тегов поверх
  всего набора данных была причиной 74 мс.
- Частичные индексы полезны не сегодня (10 000 записей читаются и так быстро),
  а по мере накопления надгробий: они не растут вместе с корзиной.
- Триграммные индексы на 10 000 записей планировщик пока не выбирает — при
  таком объёме последовательное чтение дешевле. Это ожидаемо; на 100 000+
  записей они начнут работать.
- Проверять планы стоит после каждого изменения формы запроса, а не после
  добавления индексов: индекс не спасает запрос, который не даёт его применить.

## Нагрузочный тест на боевом сервере

Замеры: **2 ноября 2026**, сервер `hal-server-879584`
(1 vCPU, 2 ГБ RAM, 50 ГБ NVMe, Ubuntu 24.04, PostgreSQL 18.6).
Данные: 200 записей одного пользователя; запросы идут с активной сессией.

Генератор — маленький скрипт на Node с фиксированной частотой (50 и 100
запросов в секунду, 20 секунд, keep-alive). Запускался **на самом сервере**:
сеть от машины разработчика даёт ~270 мс только на соединение, и любые цифры
извне показывали бы интернет, а не сервер.

### API напрямую (`127.0.0.1:8080`)

| Эндпоинт | RPS | p50, мс | p95, мс | p99, мс | max, мс | 5xx |
|---|---|---|---|---|---|---|
| `/health` | 50 | 0.7 | 1.5 | 2.6 | 5.6 | 0 |
| `/health` | 100 | 0.4 | 1.1 | 1.6 | 4.4 | 0 |
| список записей | 50 | 2.3 | **3.9** | 5.5 | 13.2 | 0 |
| список записей | 100 | 1.6 | **2.7** | 4.0 | 9.9 | 0 |
| карточка записи | 50 | 1.3 | 2.5 | 3.4 | 7.7 | 0 |
| карточка записи | 100 | 1.0 | 2.0 | 3.0 | 8.5 | 0 |
| поиск | 50 | 3.4 | **5.3** | 7.2 | 14.0 | 0 |
| поиск | 100 | 2.9 | **4.0** | 5.2 | 9.0 | 0 |

### Полный стек: HTTPS → Caddy → API

| Эндпоинт | RPS | p50, мс | p95, мс | p99, мс | max, мс | 5xx |
|---|---|---|---|---|---|---|
| список записей | 50 | 2.7 | **4.9** | 6.4 | 56.6 | 0 |
| список записей | 100 | 1.9 | **3.5** | 5.6 | 320.6 | 0 |

### Выводы

- **p95 при 50 RPS — 3.9 мс для списка и 5.3 мс для поиска.** Требование
  «< 300 мс» выполнено с запасом больше чем в 50 раз.
- **Ни одного ответа 5xx** ни на одном прогоне, включая 100 RPS.
- На 100 RPS цифры не хуже, чем на 50: узкое место ещё не наступило,
  сервер простаивает между запросами. Предел по CPU не найден — его надо
  искать на 500–1000 RPS, для чего нужен второй генератор (сам сервер
  начнёт мешать измерениям).
- **TLS почти ничего не стоит**: +1–2 мс к p95, потому что соединения
  переиспользуются.
- Единственный выброс — `max 320 мс` на HTTPS-прогоне. Это единичный
  хендшейк/планировщик на одном vCPU, p99 при этом 5.6 мс. На пользователях
  не отражается, но говорит: запас по CPU небольшой.

### Рекомендации

1. Если появится реальная нагрузка (сотни активных пользователей), первым
   шагом — **добавить vCPU**, а не переписывать запросы: при 200 записях
   база не является узким местом.
2. Статику Next отдаёт из памяти, медиа — с `immutable`-кэшем; повторные
   запросы до API не доходят, это уже экономит большую часть трафика.
3. Поиск остаётся самым дорогим эндпоинтом (5.3 мс против 3.9 мс у списка):
   при росте данных стоит проверить, что планировщик уходит с `Seq Scan` на
   триграммный индекс (см. первый раздел документа).
4. Rate limiting уже стоит на входе и регистрации; для публичного запуска
   имеет смысл добавить лимит и на чтение, чтобы один клиент не занимал CPU.
