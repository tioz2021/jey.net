# Как мы работаем

Регламент совместной работы над проектом. Короткая версия — в
[ROADMAP.md](../ROADMAP.md), здесь подробно.

## 1. Роли

**Владелец (ты)** — ставит задачи, принимает результат, говорит «коммить»,
ставит финальную оценку «нравится / не нравится». Решает продуктовые
вопросы.

**Агент (я)** — реализует ровно одну задачу, проверяет её, показывает diff,
делает коммит после разрешения. Не начинает следующую задачу сам.

## 2. Цикл работы

1. **Ты пишешь задачу.** Например: «ЗАДАЧА 5» или «делаем T15».
   Если формулировка своими словами — я найду соответствующую задачу
   в ROADMAP или предложу новую.
2. **Я беру задачу.** Ставлю ей статус `[~]` в ROADMAP, читаю описание,
   реализую **только её**.
3. **Я останавливаюсь и отчитываюсь** по шаблону из раздела 8:
   изменённые файлы, что сделано, команды проверки и их вывод, что осталось
   за рамками, предложенное сообщение коммита.
4. **Ты смотришь diff.** В VS Code — панель Source Control, или в терминале:

   ```bash
   git status
   git diff                      # изменения в уже отслеживаемых файлах
   git diff --stat               # сводка
   ```

5. **Ты проверяешь по разделу «Проверить»** в задаче и говоришь
   «нравится»/«коммить» либо «переделай вот это».
6. **Я делаю ровно один коммит** с сообщением из задачи, ставлю `[x]`,
   и жду следующую задачу.

**Правило номер один: без команды «коммить» следующий шаг не начинается.**

## 3. Правила для агента

- Не трогаю файлы, не относящиеся к задаче.
- Не расширяю объём: нашёл недочёт — предлагаю новую задачу с ID, а не чиню
  молча.
- Если задача оказалась больше описанного — останавливаюсь **до кода** и
  предлагаю разбить её на две.
- Не коммичу без явного разрешения.
- Не меняю чужие настройки (git config, редактор, систему).
- Секреты и пароли не попадают в код, логи и сообщения коммитов.
- Если проверка не проходит — не «замазываю», а сообщаю и предлагаю решение.

## 4. Правила для владельца

- Формулировка задачи может быть краткой: номер задачи в ROADMAP — этого
  достаточно.
- Замечания лучше давать по коду: файл, строка, что не так.
- Если нужно отступить от ROADMAP — это нормально, скажи, я обновлю план
  отдельным коммитом.

## 5. Коммиты

- Один коммит = одна задача.
- Формат сообщения — Conventional Commits:

  ```
  feat(auth): add registration endpoint
  fix(items): reject empty title
  docs: describe api contract
  ```

- Сообщение берётся из строки **Коммит:** соответствующей задачи.
- В тело коммита можно добавить: `Refs: T15`.
- Ветка — `main`. Ветки под задачи не заводим: история и так линейная
  и по одному коммиту на задачу.
- Пуш в GitHub — после того как накопится несколько коммитов, отдельной
  командой.

## 6. Статусы задач

| Статус | Значение |
|---|---|
| `[ ]` | не начата |
| `[~]` | в работе (я поставил) |
| `[x]` | принята и закоммичена |
| `[!]` | заблокирована, причина в строке |

`[~]` ставлю я при старте, `[x]` — в том же коммите, который ты одобрил.

## 7. Definition of Done

Задача считается выполненной, когда:

1. Код собирается: `cargo build` (для фронтенда — `npm run build`).
2. Нет предупреждений: `cargo clippy -- -D warnings`.
3. Форматирование: `cargo fmt --check`.
4. Тесты, если они предусмотрены задачей, зелёные.
5. Ручная проверка из раздела «Проверить» выполнена и её вывод показан.
6. README/документация обновлены, если изменилось поведение или контракт.
7. Ты сказал «коммить».
8. Чекбокс задачи переведён в `[x]`, а строка «Текущий статус» в ROADMAP
   обновлена — **в том же коммите**, а не отдельным.


## 9. Если что-то пошло не так

- **Тест упал** — показываю вывод, предлагаю вариант исправления, не коммичу.
- **Задача противоречит документации** — останавливаюсь, показываю
  противоречие, предлагаю поправить документ отдельной задачей.
- **Нашёл баг вне задачи** — завожу предложение `TXX` в ROADMAP, но не чиню.
- **Проверка требует недоступного окружения** (например, облачной БД) —
  сообщаю и предлагаю, как обойти.

## 10. Веб-первый цикл новых фич

С 13 ноября 2026 новый функционал сначала появляется в веб-версии и только
потом переносится в desktop. Это снижает риск сломать локальную библиотеку
и синхронизацию.

### Этапы

```text
1. Веб + API + БД
2. Тесты веба
3. Перенос в desktop
4. Тесты desktop
5. Релиз
```

#### 1. Веб + API + БД

- миграции и API;
- экран, состояния загрузки/пустоты/ошибки;
- RU/UK/EN;
- адаптивность;
- деплой на `j3ynet.site`.

#### 2. Тесты веба

- API-тесты и миграции;
- `npm run build`;
- Puppeteer на desktop/mobile viewport;
- ручная проверка основного сценария.

Только после этого функционал считается готовым к desktop.

#### 3. Перенос в desktop

- bridge и local fallback;
- SQLite-схема и миграции;
- outbox/sync, если появились новые данные;
- офлайн-сценарии;
- сборка `0.3.x`.

#### 4. Тесты desktop

- реальный сценарий в окне;
- перезапуск;
- офлайн → online;
- отсутствие регрессии detail/list/sync;
- при необходимости — ручная проверка на Windows/Linux.

#### 5. Релиз

- changelog;
- patch/minor версия;
- артефакты;
- проверка checksum.

### Правила

1. Новый функционал не начинается сразу в desktop.
2. Web-фича не считается готовой, пока не прошла тесты веба.
3. Desktop-интеграция не начинается, пока веб не задеплоен и не проверен.
4. Одна фича — один понятный набор коммитов; не смешивать с рефакторингом.
5. Если фича требует новых данных, сначала проектируется контракт API и sync.
6. Если веб-фича не имеет смысла офлайн, в desktop она может остаться
   серверной; это нужно явно указать.
7. Найденный вне задачи баг фиксируется отдельно, а не «заодно».

