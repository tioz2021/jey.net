# Архитектура

Документ описывает, **как** устроен портал: компоненты, потоки данных,
модель данных и принятые решения. Продуктовые требования — в
[spec.md](spec.md), контракт API — в [protocol.md](protocol.md).

## 1. Общая схема

```
                 ┌──────────────────────────────┐
   Браузер ──────►│  Caddy (TLS, статика, прокси)│
                 └───────┬──────────────┬───────┘
                         │              │
              /api/v1/*  │              │  /  (SSR/статика)
                         ▼              ▼
                 ┌───────────────┐  ┌──────────────┐
                 │  jey-api      │  │  frontend    │
                 │  Rust + axum  │  │  Next.js     │
                 └───┬───────┬───┘  └──────────────┘
                     │       │
                     │       └──────────► Cloudflare R2 (медиа)
                     ▼
              ┌──────────────┐
              │  PostgreSQL  │
              └──────────────┘
```

Компоненты:

- **jey-api** — единственный владелец бизнес-логики и данных. Никакой прямой
  доступ к БД из фронтенда.
- **frontend** — Next.js: страницы, формы, состояние. Ходит только в API.
- **PostgreSQL** — источник истины. Миграции — часть репозитория.
- **R2** — файлы. В БД хранятся только ключи и метаданные.
- **Caddy** — TLS, сжатие, заголовки безопасности, раздача статики, прокси.

Один VPS на старте: Caddy + api + Postgres + собранный фронтенд. Разделение
на отдельные машины — задача на потом, архитектура это допускает (API
stateless, файлы в объектном хранилище).

## 2. Структура репозитория

```
backend/            Rust-крейт jey-api
  src/
    main.rs         точка входа, сборка приложения
    config.rs       конфигурация из окружения
    telemetry.rs    логирование, request id
    error.rs        AppError и JSON-ошибки
    db.rs           пул соединений
    auth/           пароли, сессии, middleware
    items/          домен записей
    http/           роутер и хендлеры
  tests/            интеграционные тесты
frontend/           Next.js-приложение
migrations/         SQL-миграции (sqlx)
scripts/            локальные проверки
docs/               проектная документация
```

Правило: домены (`auth`, `items`, `media`) не знают про HTTP. HTTP-слой
превращает запрос в вызов домена и результат в JSON.

## 3. Модель данных

### users

| Поле | Тип | Примечание |
|---|---|---|
| id | uuid pk | генерируется приложением |
| email | citext unique | хранится в нижнем регистре |
| email_verified_at | timestamptz null | null — не подтверждён |
| password_hash | text | argon2id, PHC-строка |
| display_name | text | 1–60 символов |
| locale | text | `ru` по умолчанию |
| is_public | bool | публичный профиль |
| created_at, updated_at | timestamptz | |
| deleted_at | timestamptz null | мягкое удаление |

### sessions

| Поле | Тип | Примечание |
|---|---|---|
| id | uuid pk | |
| user_id | uuid fk | on delete cascade |
| token_hash | bytea unique | sha256 от токена; сам токен не хранится |
| created_at, last_seen_at | timestamptz | |
| expires_at | timestamptz | 30 дней |
| ip | inet | для диагностики |
| user_agent | text | обрезается до 512 |

### items

| Поле | Тип | Примечание |
|---|---|---|
| id | uuid pk | |
| user_id | uuid fk | индекс |
| kind | text | `movie`, `book`, `image`, `other` |
| title | text | 1–300 |
| subtitle | text null | режиссёр/автор |
| year | int null | 1800–2100 |
| status | text | см. spec |
| rating | smallint null | 1–10 |
| review | text null | до 20 000 символов |
| source_url | text null | ссылка на источник |
| cover_key | text null | ключ файла в хранилище |
| meta | jsonb | тип-специфичные поля |
| created_at, updated_at | timestamptz | |
| deleted_at | timestamptz null | корзина |

Индексы: `(user_id, created_at desc)`, `(user_id, kind)`, `(user_id, status)`,
GIN по `to_tsvector`-выражению и `pg_trgm` для поиска.

### tags и item_tags

`tags(id, user_id, name)` с уникальностью `(user_id, lower(name))`;
`item_tags(item_id, tag_id)` с каскадным удалением.

### uploads

`uploads(id, user_id, key, mime, size, width, height, created_at)` — реестр
файлов для учёта квот и сборки мусора.

### auth_tokens

Одноразовые токены для подтверждения email и сброса пароля:
`(id, user_id, purpose, token_hash, expires_at, used_at)`.

## 4. Жизненный цикл запроса

1. Caddy принимает TLS и проксирует `/api/v1/*` в `jey-api`.
2. Middleware: `X-Request-Id` (или генерация), логирование, лимит тела,
   проверка Origin для небезопасных методов.
3. Извлечение сессии: cookie → sha256 → поиск в `sessions` → пользователь.
4. Хендлер валидирует вход, вызывает домен, получает результат.
5. Ответ: JSON по контракту; ошибки — единый формат с кодом и `request_id`.
6. Лог: метод, путь, статус, длительность, `request_id`, id пользователя.

## 5. Безопасность

- **Пароли**: argon2id, параметры подбираются замером (цель ~250 мс).
- **Сессии**: 32 байта CSPRNG, в БД только SHA-256; cookie `HttpOnly`,
  `Secure` в проде, `SameSite=Lax`, `Path=/`.
- **CSRF**: `SameSite=Lax` + обязательная проверка `Origin`/`Referer` для
  POST/PATCH/DELETE.
- **Перебор**: лимиты на вход и регистрацию по IP и email, задержка при
  неудаче, блокировка после серии попыток.
- **Валидация**: только на бэкенде; фронтенд дублирует для удобства.
- **SQL**: исключительно параметризованные запросы sqlx, без конкатенации.
- **XSS**: React экранирует по умолчанию; `dangerouslySetInnerHTML` запрещён.
- **Файлы**: проверка MIME по содержимому, лимит размера, перекодирование
  изображений, отдача с `Content-Disposition` и отдельного домена/пути.
- **Заголовки**: CSP, `X-Content-Type-Options`, `Referrer-Policy`,
  `Strict-Transport-Security`.
- **Секреты**: только в `.env` с правами `600`, не в git, не в логах.

## 6. Масштабирование

Порядок действий при росте нагрузки — от дешёвого к дорогому:

1. Кэш статики и изображений на CDN.
2. Индексы и оптимизация запросов (замеры `EXPLAIN ANALYZE`).
3. Вынос фронтенда на CDN/Vercel — API остаётся один.
4. Вертикальный апгрейд VPS.
5. Отдельная машина под Postgres.
6. Несколько инстансов API за Caddy (сессии уже в БД, API stateless).

## 7. Решения и компромиссы

| Решение | Альтернатива | Почему так |
|---|---|---|
| Rust + axum | C++, Go, Node | Безопасность памяти, зрелая экосистема, один бинарник |
| Postgres | SQLite | Нужны конкурентная запись, полнотекстовый поиск, рост |
| Сессии в БД | JWT | Отзыв сессии, простота, нет проблем с ротацией ключей |
| Отдельный фронтенд | SSR из Rust | Экосистема UI, независимый деплой, будущее мобильное приложение |
| R2 | Диск VPS | 50 ГБ диска мало для медиа, дешёвый трафик, бэкапы |
| Мягкое удаление | Жёсткое | Корзина и защита от случайной потери |

## 8. Ограничения текущей среды

Разработка идёт на Fedora с rustup-тулчейном; Docker и `sudo` недоступны,
поэтому:

- база для разработки — облачный Postgres (Neon);
- интеграционные тесты используют отдельную тестовую БД;
- сборка и проверки — локальные скрипты и GitHub Actions.
