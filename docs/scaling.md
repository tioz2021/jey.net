# План роста jey.net

Документ отвечает на вопрос: **что делать, когда пользователей станет больше 100**.
Оценки ориентировочные; точные цифры даёт нагрузочный тест на конкретном VPS.

Текущая инфраструктура:

```text
1 vCPU
1.9 GB RAM
PostgreSQL на том же VPS
один API-инстанс
```

Текущая оценка: **~100 активных пользователей — комфортно**, несколько сотен
открытых вкладок/SSE — вероятно, выдержит. Это не жёсткий предел, а запас
текущего VPS.

## Принципы

1. Сначала вертикальное масштабирование, потом горизонтальное.
2. PostgreSQL — главный общий ресурс; второй API не удваивает БД.
3. Деградировать постепенно: `429`, таймауты, fallback на polling, а не отказ.
4. Desktop local-first продолжает работать без сервера.
5. Апгрейд делается по метрикам, а не по «ощущению».

## Этапы роста

| Активных | Действие |
|---:|---|
| 100–200 | наблюдать метрики, ничего не менять |
| 200–300 | вертикальный апгрейд: 2–4 vCPU, 4–8 GB RAM |
| 300–500 | оптимизация БД, индексы, connection pool, CDN для статики/media |
| 500–1000 | второй API + T190 + общий media + managed PostgreSQL |
| 1000+ | HA PostgreSQL, отдельный load balancer, кэширование |

## Мониторинг и триггеры

Смотреть:

```text
p95 latency
5xx rate
API CPU
PostgreSQL connections
SSE connections
disk usage
429 rate
```

Триггеры:

```text
p95 > 200 ms в течение 5 минут      → апгрейд CPU / разбор запросов
CPU > 70% на пике                  → вертикальный апгрейд
PostgreSQL connections > 70%       → pool tuning / апгрейд БД
5xx > 1%                           → немедленный разбор
disk > 80%                         → чистка media/backups
```

Не ждать полного отказа: при росте сначала растёт latency, потом появляются
`429/502/504`.

## Этап 1 — вертикальный апгрейд

Первое действие при 200–300 активных:

```text
2–4 vCPU
4–8 GB RAM
```

Почему: API и PostgreSQL сейчас делят одно ядро. Это самый дешёвый и
безопасный шаг, не требующий изменений кода.

После апгрейда повторить `scripts/load-test.py` и зафиксировать новый baseline.

## Этап 2 — база и статика

- проверить slow queries и индексы;
- ограничить pool размером, который выдерживает PostgreSQL;
- вынести статику/media в CDN или object storage;
- включить gzip/brotli и immutable cache для assets;
- проверить, что публичные страницы не ходят лишний раз в БД.

## Этап 3 — два API-инстанса

Перед вторым инстансом обязательно:

- [ ] T190: cross-instance уведомления через PostgreSQL `LISTEN/NOTIFY`;
- [ ] общий media storage для всех инстансов;
- [ ] один owner фоновых задач (backup, push, cleanup);
- [ ] балансировщик перед API;
- [ ] миграции выполняются один раз;
- [ ] SSE не буферизуется прокси;
- [ ] health/readiness для каждого инстанса;
- [ ] T202 пересмотрен: второй инстанс действительно нужен.

Если этого нет, два инстанса дадут не масштабирование, а рассинхронизацию:
часть пользователей не увидит уведомления, обложки могут пропадать,
фоновые задачи будут выполняться дважды.

## Этап 4 — HA

Для настоящей отказоустойчивости:

- managed PostgreSQL или primary/standby;
- два API на разных VPS;
- внешний load balancer;
- общий object storage для media;
- отдельный worker;
- резервный канал backup/restore.

Два API на одном VPS не являются HA: VPS и БД остаются единой точкой отказа.

## Ограничения, которые не про CPU

- публичные endpoints: **300 запросов/минуту на IP**;
- регистрация: **3 в час на IP**;
- пользователи за одним офисным NAT могут получить `429` раньше, чем
  закончится CPU;
- SSE уведомлений сейчас in-process, поэтому второй инстанс без T190
  оставит часть клиентов без live-событий (polling-fallback останется).

## Нагрузочный тест

```bash
python3 scripts/load-test.py \
  --base-url http://127.0.0.1:8091 \
  --scenario auth \
  --vus 50 \
  --seconds 10
```

Сценарии:

```text
public  — health/public users
auth    — items/stats/me
sse     — notification streams
```

Результаты и ADR: [load-test.md](load-test.md).

## Правило решения

Не поднимать второй инстанс «на всякий случай».

Порядок:

```text
метрики → вертикальный апгрейд → оптимизация БД/static
→ T190 + общий media + worker
→ второй API
```

Если после вертикального апгрейда p95 и CPU в норме — второй инстанс не нужен.
