# Технологический стек

Документ фиксирует, на чём делаем и **почему именно на этом**. Версии
указаны на момент старта (ноябрь 2026) и уточняются при первом коммите
в `Cargo.toml` / `package.json`.

## 1. Структура проекта

Проект — Cargo-воркспейс из трёх крейтов и одного фронтенда:

| Крейт | Что внутри | Зависит от |
|---|---|---|
| `jey-core` | доменные типы, валидация, репозиторные трейты, правила слияния | ничего, кроме `serde`, `uuid`, `time` |
| `jey-api` | axum, sqlx, PostgreSQL, синхронизация, почта | `jey-core` |
| `jey-desktop` | Tauri, SQLite, офлайн-операции, кнопка Sync | `jey-core` |

Правило: `jey-core` не зависит ни от `axum`, ни от `sqlx`. Именно это
позволяет использовать одну доменную логику на сервере и на устройстве.

## 2. Бэкенд

| Компонент | Выбор | Версия | Зачем |
|---|---|---|---|
| Язык | Rust | 1.99.1, edition 2024 | безопасность памяти, один бинарник, предсказуемая производительность |
| HTTP | axum | 0.8.x | минималистичный, на tower-сервисах, отличная композиция middleware |
| Runtime | tokio | 1.x | стандарт де-факто для асинхронного Rust |
| Middleware | tower, tower-http | 0.5 / 0.7 | трейсинг, лимиты тела, таймауты, CORS |
| БД | sqlx | 0.9.x | SQL без ORM, проверка запросов, миграции, пул |
| Пароли | argon2 | 0.6.x | argon2id, современный стандарт |
| Сериализация | serde, serde_json | 1.x | JSON-контракт |
| Время | chrono | 0.4.x | timestamptz ↔ RFC 3339 |
| UUID | uuid | 1.x | идентификаторы |
| Логи | tracing, tracing-subscriber | 0.1 / 0.3 | структурированные логи, request id |
| Конфиг | dotenvy + собственный модуль | 0.15 | без магии, с валидацией на старте |
| Ошибки | thiserror | 2.x | типизированные ошибки домена |
| Картинки | image | 0.25.x | ресайз и перекодирование в WebP |
| Почта | трейт `Mailer`, dev-транспорт в файлы | — | локально письма в `var/mail/`, в проде — внешний API (Brevo/Resend), без своего SMTP |

Принципы:

- **Никакого ORM.** SQL пишется руками, запросы проверяются `sqlx::query!`
  там, где есть живая БД, иначе — `query_as` с типизированным маппингом.
- **Домен не знает про HTTP.** Хендлеры тонкие, логика в модулях.
- **Ошибки типизированы.** `AppError` → HTTP-статус и код из
  [protocol.md](protocol.md).

## 3. База данных

**PostgreSQL 18** — конкурентная запись, оконные функции для статистики,
`pg_trgm` для поиска, зрелые бэкапы.

Миграции — обычные SQL-файлы в `migrations/`, применяются `sqlx migrate`.
Правила:

- миграции только добавляющие (новая колонка — nullable или с дефолтом);
- разрушающие изменения — отдельным релизом, после выноса кода;
- каждая миграция проверяется на чистой БД и на копии продовой.

Версии локальной базы и базы на VPS должны совпадать по мажору. На Fedora
ставится Postgres 18 из репозитория дистрибутива, на Ubuntu 24.04 (VPS) —
18 из репозитория PGDG, потому что в дистрибутиве там только 16.

Разработка ведётся против локального Postgres: быстрее, работает офлайн и не
зависит от внешних сервисов. Облачный Postgres (Neon) — запасной вариант на
случай, если понадобится база, доступная с нескольких машин.

## 4. Фронтенд

| Компонент | Выбор | Зачем |
|---|---|---|
| Фреймворк | Next.js (App Router) | SSR для публичных страниц, статика для остального |
| Язык | TypeScript | типы совпадают с контрактом API |
| Стили | Нативный CSS + CSS Modules | полный контроль над разметкой, без утилит и Tailwind |
| Компоненты | собственные, на CSS Modules | shadcn/ui требует Tailwind, поэтому пишем сами |
| Формы | react-hook-form + zod | валидация на клиенте и типы из схемы |
| Данные | fetch + Server Actions / TanStack Query | без лишнего слоя |

Правила:

- только нативный CSS: CSS Modules для компонентов, переменные в `globals.css`;
- допустимы современные возможности: `nesting`, `:has()`, container queries;
- никакого `dangerouslySetInnerHTML`;
- все состояния: загрузка, пусто, ошибка;
- мобильная вёрстка от 360 px;
- строки интерфейса — в одном модуле, чтобы позже добавить локализацию.

## 5. Десктоп

| Компонент | Выбор | Зачем |
|---|---|---|
| Оболочка | Tauri 2 | бинарник ~10 МБ, системный WebView, Rust внутри |
| Локальная БД | SQLite (sqlx) | файл на диске, WAL, нечего устанавливать |
| Интерфейс | тот же фронтенд | одна вёрстка для веба и десктопа, статическая сборка |
| Синхронизация | `jey-core` + `/sync/*` | один протокол для всех клиентов |
| Упаковка | AppImage, .deb | запуск без установки зависимостей |

Почему Tauri, а не Electron: Electron тащит Chromium (~150 МБ) и Node,
Tauri использует системный WebView и тот же Rust-код, что и сервер.

## 6. Инфраструктура

| Компонент | Выбор | Зачем |
|---|---|---|
| VPS | 1–2 vCPU, 2 ГБ RAM, Ubuntu 24.04 | хватает на старте; сервер — хаб синхронизации, а не единственная копия данных |
| Reverse proxy | Caddy 2 | автоматический TLS, сжатие, заголовки |
| Процесс | systemd | без Docker: меньше памяти и слоёв |
| Файлы | локальный диск VPS (`var/media/`) | минимум движущихся частей; 40 ГБ хватает на годы при лимите 200 МБ на пользователя |
| Объектное хранилище | Cloudflare R2 | только резервные копии; бесплатного тарифа достаточно |
| CI | GitHub Actions | сборка, тесты, деплой артефактов |
| Мониторинг | внешний uptime-чек + `tracing` в файлы + алерты | минимально достаточно |
| Бэкапы | `pg_dump` и медиа в R2 по расписанию | восстановление проверяется раз в месяц |

Медиа начинают на локальном диске, потому что на старте это проще и дешевле:
нет внешней зависимости, нет подписи запросов, всё работает офлайн. Слой
хранилища абстрагирован, поэтому переезд на R2 — задача на один день, если
появится вторая машина или объём перестанет влезать на диск. Резервные копии
при этом сразу уходят в R2: 10 ГБ бесплатного тарифа хватает на дампы БД и
изображения.

## 7. Инструменты разработки

- `rustfmt` + `clippy` (`-D warnings`) — обязательны в CI;
- `cargo audit` — проверка уязвимостей зависимостей;
- `sqlx-cli` — миграции и подготовка офлайн-кэша запросов;
- `eslint` + `prettier` для фронтенда;
- `scripts/check.sh` — единая локальная проверка перед коммитом.

## 8. Политика версий

- Версии крейтов фиксируются в `Cargo.lock`, коммитится.
- Обновления — отдельными задачами, не «попутно».
- Мажорные обновления (axum, sqlx, Next.js) — только с прогоном тестов и
  чтением changelog.
- Зависимости добавляются осознанно: каждая должна закрывать задачу, которую
  неразумно писать самому.

## 9. Ограничения среды

Разработка ведётся на Fedora 44, GNOME/Wayland:

- нет `sudo` и Docker — поэтому нет локального Postgres и контейнеров;
- Rust установлен через rustup (`~/.cargo/bin`), версия 1.99.1;
- Node.js 22 доступен;
- редактор — VS Code (Flatpak) с rust-analyzer.

## 10. Что рассматривали и отвергли

| Вариант | Почему нет |
|---|---|
| **C++** | медленнее в разработке, нет зрелой экосистемы для auth/БД/HTTP, выше риск уязвимостей в security-коде; выигрыш в производительности для этой задачи нерелевантен |
| **Go** | технически хорош, но неинтересен владельцу проекта; код должен хотеться читать |
| **Node/TypeScript на бэкенде** | допустимо, но слабее типизация домена и выше риск ошибок в конкурентном коде |
| **SQLite** | не подходит для конкурентной записи и роста; миграция позже дороже |
| **JWT вместо сессий** | нельзя отозвать токен, сложнее ротация ключей, не нужен stateless-сценарий |
| **Docker на VPS** | лишние 100–200 МБ RAM на 2 ГБ машине; systemd проще |
| **Electron** | тяжёлый рантайм, вторая копия Chromium, больше памяти |
| **PWA вместо десктопа** | офлайн-сценарий закрывает десктопное приложение, PWA остаётся запасным вариантом |
| **CRDT (Automerge, Loro)** | сложность не оправдана для личных записей; LWW по записи достаточно |
| **ORM (Diesel, SeaORM)** | скрывает SQL; для статистики и сложных фильтров нужен ручной контроль |

## 11. Критерии выбора зависимостей

1. Активно поддерживается, есть релизы за последние 6 месяцев.
2. Не тянет за собой десятки транзитивных крейтов без необходимости.
3. Лицензия совместима с закрытым использованием (MIT/Apache-2.0).
4. Есть документация и примеры, а не только README.
5. Можно заменить: слой изолирован, а не размазан по коду.
