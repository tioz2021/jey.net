# Универсальная запись

Статус: черновик спецификации. Код ещё не реализован.

## 1. Зачем

Сейчас `items` — это каталог фильмов, книг, игр и аниме. Для главной идеи
jey.net нужен один тип записи, которым можно описать:

- фильм и сериал;
- книгу;
- игру;
- аниме;
- заметку;
- ссылку;
- изображение;
- видео;
- музыку или плейлист.

Тип меняет поля и внешний вид карточки, но не создаёт отдельную таблицу,
отдельный API и отдельный экран.

## 2. Принципы

1. **Одна таблица `items`** — одна запись с общим ядром и типизированным
   `meta`.
2. **Тип — это поведение, а не отдельная сущность.** `kind` определяет
   валидацию, иконку, поля редактора и блоки публичной карточки.
3. **Общие поля обязательны, специфичные — в `meta`.** Не превращать таблицу
   в набор nullable-колонок под каждый сервис.
4. **Личная заметка и публичная рецензия — разные поля.**
5. **Существующие записи и URL не ломаются.**
6. **Синхронизация проектируется сразу.** Клиент сможет создать запись
   офлайн, а сервер примет её по `id`.

## 3. Типы

```text
movie   — фильм
tv      — сериал
book    — книга
game    — игра
anime   — аниме
note    — заметка
link    — ссылка
image   — изображение
video   — видео
music   — музыка, альбом, плейлист
other   — прочее
```

`image` и `other` уже есть в `ItemKind`; `note`, `link`, `video`, `music`
нужно добавить. Список расширяемый, но только через миграцию и валидацию.

## 4. Модель записи

### Общие поля

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `id` | uuid | да | клиентский UUID, одинаковый на устройствах |
| `user_id` | uuid | да | владелец |
| `kind` | text | да | тип записи |
| `title` | text | да | название; для заметки — первая строка или «Без названия» |
| `subtitle` | text | нет | автор, студия, канал, альбом |
| `year` | int | нет | год выпуска |
| `status` | text | да | `planned`, `in_progress`, `done`, `dropped`, `saved` |
| `rating` | int 1–10 | нет | оценка |
| `review` | text | нет | **публичная** заметка/рецензия |
| `body` | text | нет | **приватная** заметка в Markdown |
| `source_url` | text | нет | исходная ссылка |
| `cover_key` | text | нет | обложка в хранилище |
| `meta` | jsonb | да | типизированные поля по `kind` |
| `meta_version` | int | да | версия схемы `meta` |
| `visibility` | text | да | `private` или `public` |
| `progress_current` | int | нет | текущий прогресс |
| `progress_total` | int | нет | всего |
| `progress_unit` | text | нет | `episode`, `page`, `hour`, `track` |
| `revision` | bigint | да | клиентская ревизия |
| `sync_seq` | bigint | да | серверная последовательность |
| `device_id` | uuid | нет | последнее устройство |
| `created_at` | timestamptz | да | создание |
| `updated_at` | timestamptz | да | последнее изменение |
| `deleted_at` | timestamptz | нет | надгробие |
| `slug` | text | да | уникален внутри пользователя |

`review` остаётся публичным, как сейчас. `body` — новое поле и **никогда не
попадает на публичную страницу**.

### Статусы по типам

| Тип | Допустимые статусы |
|---|---|
| movie, tv, book, game, anime | planned, in_progress, done, dropped |
| note, link, image | saved |
| video, music | saved, planned, in_progress, done, dropped |

Для не-медиа статус можно не показывать в интерфейсе. В БД он остаётся
`NOT NULL DEFAULT 'saved'`, чтобы не плодить nullable-состояния.

### Видимость

`visibility` — главный переключатель публичности записи.

- `private` — видит только владелец;
- `public` — запись доступна по публичному URL.

Старые `public_hidden` и `users.public_statuses` остаются для совместимости
на время миграции. После неё публичная выдача должна опираться на
`visibility`, а не на статус записи.

Рекомендуемое поведение для новых записей — **private по умолчанию**, даже
если профиль публичный. Это особенно важно для заметок и изображений.

## 5. `meta` по типам

`meta` — JSONB с версией. Валидация выполняется Rust-типами, а не «чем
угодно».

### movie / tv

```json
{
  "version": 1,
  "runtime_minutes": 169,
  "director": "Wolfgang Petersen",
  "cast": ["Brad Pitt", "Eric Bana"],
  "genres": ["drama", "history"],
  "countries": ["USA"],
  "seasons": 1,
  "episodes": 10,
  "watched_episodes": [{"season": 1, "episode": 1}]
}
```

`details` (TMDB) остаётся кэшем метаданных на время миграции.

### book

```json
{
  "version": 1,
  "authors": ["..."],
  "pages": 416,
  "publisher": "...",
  "isbn": "..."
}
```

### game

```json
{
  "version": 1,
  "platforms": ["PC", "PS5"],
  "hours": 42,
  "achievements": 18,
  "store": "steam"
}
```

### anime

```json

  "version": 1,
  "studio": "...",

  "season": "fall",
  "year": 2026

```

### note

```json

  "version": 1,
```

### link

## 6. Вложения и коллекции

### `record_assets`

Одна запись может иметь несколько файлов:

```text
id, record_id, role, storage_key, mime, width, height, bytes, position
```

`role`: `cover`, `gallery`, `attachment`, `preview`.

`cover_key` остаётся для обратной совместимости; новые изображения
записываются в `record_assets`.

### `collections`

Коллекция — это полка, доска или плейлист:

```text
id, user_id, title, slug, kind, visibility, cover_asset_id, created_at
```

```text
record_collections(record_id, collection_id, position)
```

Примеры:

- «Посмотрел в 2026»;
- «Хочу прочитать»;
- «Сохранённое с YouTube»;
- «Вдохновение»;
- «Мой плейлист».

Коллекция может быть приватной или публичной. Одна запись может входить в
несколько коллекций.

## 7. URL и публичные страницы

Сохраняем текущую схему:

```text
/u/{handle}/cart/{slug}   — публичная карточка
/u/{handle}/item/{slug}   — своя карточка
```

Меняется только содержимое карточки: оно выбирается по `kind`.

Публичная страница показывает:

- `review`, но не `body`;
- `meta` в объёме, разрешённом типом;
- обложку и галерею;
- комментарии и реакции.

Публичный профиль показывает записи с `visibility = 'public'`, а не
«все записи с публичным статусом».

## 8. API

Остаётся единый ресурс `/items`, но с полями универсальной записи.

### Создание

```json
{
  "id": "клиентский UUID",
  "kind": "note",
  "title": "Мысли о поездке",
  "body": "Markdown...",
  "visibility": "private",
  "status": "saved",
  "meta": {"version": 1, "format": "markdown"},
  "collections": ["trips"]
}
```

### Изменение

`PATCH /items/{id}` принимает те же поля. `meta` валидируется по `kind` и
`meta_version`.

### Чтение

- `GET /items/{id}` — владелец;
- `GET /items` — фильтры по `kind`, `status`, `collection`, `q`;
- публичные страницы — существующие `/public/...` endpoints.

### Ответ

В ответе всегда есть общие поля и `meta`; фронтенд выбирает renderer по
`kind`, а не по названию endpoint.

## 9. Синхронизация

Используем уже описанный [протокол](sync.md), расширяя сущность `item`.

Клиентская SQLite-схема повторяет общие поля плюс:

```text
dirty, last_synced_at, local_asset_path
```

Правила:

- клиент создаёт UUID сам;
- `revision` растёт на клиенте;
- сервер присваивает `sync_seq`;
- удаление — только `deleted_at`;
- `body`, `review`, `meta`, `visibility` входят в payload;
- вложения синхронизируются отдельно по хэшу;
- конфликт сохраняется как копия, без молчаливой потери.

## 10. Миграция текущих `items`

Не переименовывать таблицу сразу. Добавить колонки и типы:

1. `body text`, `visibility text NOT NULL DEFAULT 'private'`,
   `meta_version int NOT NULL DEFAULT 1`,
   `progress_current int`, `progress_total int`, `progress_unit text`.
2. Расширить `items_kind_known`: `note`, `link`, `video`, `music`.
3. Разрешить `saved` в `items_status_known`; для старых записей оставить
   текущие статусы.
4. Заполнить `visibility = 'public'` для записей, которые уже видны публично
   по текущим правилам, остальные — `private`.
5. Создать `record_assets` и `collections`.
6. Постепенно перенести `details` в `meta` для movie/tv; старый `details`
   оставить как кэш до отдельного решения.

После миграции фронтенд должен уметь показывать старые записи без изменений.

## 13. Что не входит

- полноценная замена Obsidian: граф, плагины, backlinks;
- бесконечная лента Pinterest;
- воспроизведение Spotify;
- скачивание YouTube или книг;
- отдельные приложения под каждый тип.
